# Test & Evaluation Plan

**Project:** Fine-Tuned Vision-Language Model for Scanned Document Extraction
**Status:** Draft v1.0
**Last updated:** 2026-09-08

---

## 1. Purpose

Define exactly what will be measured, how, against what baselines, and
what counts as a meaningful result — decided **before** training, so
results can't be cherry-picked or re-scoped after the fact.

## 2. The one headline comparison

To keep the project defensible and avoid a sprawling matrix (see PRD §4,
Non-goals), there is exactly **one primary comparison** and **one
secondary reference point**:

- **Primary:** Fine-tuned small VLM (Donut, LoRA) vs. OCR+rules baseline
  (the real production-analogous failure mode, ~10% accuracy)
- **Secondary (sanity check only):** Zero-shot large VLM (Claude/GPT-4V),
  same test set — included to show awareness of the alternative, not to
  build a full competing pipeline around it

Any additional experiment (e.g., Qwen2-VL-7B as a stretch comparison,
Stage-1 generic-document warm-up ablation) is explicitly labeled as
**bonus/exploratory**, not part of the headline result.

## 3. Metrics

| Metric | Definition | Why it matters |
|---|---|---|
| Field-level Precision/Recall/F1 | Per field (account_number, ifsc_code, balances, dates, etc.) | Whole-record exact match is too harsh — one wrong field shouldn't zero out a correct record |
| Accuracy by degradation tier | F1 computed separately for clean / light / medium / heavy tiers | Shows *where* the model breaks down, not just an average |
| Generalization score | F1 on the held-out, never-trained-on template variant | Tests whether the model learned the task or memorized layouts |
| Cost per document | API cost (zero-shot) vs. amortized inference cost (fine-tuned, self-hosted) | Makes the result a practical, not just academic, argument |
| Latency per document | Wall-clock inference time, both paths | Same reasoning as cost |

**Field matching rules:**
- Exact match required for: account numbers, IFSC/MICR codes, dates, amounts
- Fuzzy match (normalized edit distance, threshold TBD during eval script
  build) allowed for: names, free-text descriptions

## 4. Test set construction

- 15% of the full dataset, stratified by degradation tier and template
  type (see Technical Design Doc §2.3)
- One entire template variant excluded from training and validation,
  reserved only for the generalization test (§3, "Generalization score")
- Test set is **touched exactly once**, at the end, for final reported
  numbers — never used to pick checkpoints or tune hyperparameters

## 5. Baseline reproduction

- OCR+rules baseline number (~10%) is taken as the known, previously
  observed production result — not re-run in this project (that pipeline
  is the employer's, not reproducible on public data 1:1). This will be
  clearly labeled as a **reported reference figure**, not a number
  generated by this project's own code, in the final write-up.
- Zero-shot large VLM baseline **is** run directly by this project, on
  the same test set, so that comparison is fully reproducible and fair.

## 6. Acceptance criteria (what counts as a meaningful result)

The project is considered a successful proof-of-concept if:

- [ ] The fine-tuned model achieves a materially higher field-level F1
      than the zero-shot baseline on at least the medium/heavy degradation
      tiers (this is the core hypothesis — fine-tuning should help most
      exactly where generic models struggle most)
- [ ] The fine-tuned model's inference cost per document is meaningfully
      lower than the large-model API cost per document
- [ ] Results are reported honestly even if the hypothesis is *not*
      confirmed — a negative or mixed result (e.g., zero-shot wins on
      clean docs but fine-tuning wins on degraded ones) is still a valid,
      reportable finding and should be written up as such, not hidden

## 7. What "failure" would look like, and how to report it

If the fine-tuned model does **not** outperform zero-shot:
- Report the gap honestly, and analyze *why* (insufficient data volume,
  degradation mismatch vs. real documents, Donut's capacity ceiling, etc.)
- This is still a legitimate, presentable finding — "I tested the
  hypothesis, found it didn't hold under X condition, and here's my
  analysis of why" is a stronger interview answer than an inflated,
  cherry-picked win.

## 8. Reproducibility checklist

- [ ] Random seed fixed for train/val/test split
- [ ] Degradation pipeline parameters version-controlled/logged per tier
- [ ] Training config (LoRA rank/alpha, learning rate, epochs) logged per run
- [ ] Evaluation script run identically against both the fine-tuned model
      and the zero-shot baseline (same scoring code, no separate logic)
